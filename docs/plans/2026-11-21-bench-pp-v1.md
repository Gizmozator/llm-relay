# Plan: Benchmark prompt-processing (PP) speed

- **Status:** done
- **Owner:** maintainer
- **Started:** 2026-11-21
- **Issue:** —
- **Supersedes / superseded by:** —

## Goal

The model benchmark measures only decode speed (TG). Extend it to also measure
prompt-processing (PP) speed with a ~10k-token input, store it per model, show
it in the admin and public catalogs next to the TG speed, and prefill the price
calculator's "Prompt-processing speed" input from it.

## Non-goals

- No per-run history — like TG, only the latest measurement is stored.
- No queue/load awareness beyond the existing serialization (`benchMu`): a
  busy engine skews PP just like it skews TG.
- No separate "PP only" button — one Benchmark click runs both passes.

## Current state

- `AdminBenchmarkModel` (`internal/api/admin.go`): one timed streaming
  generation (natural prose, 700 max tokens), TG = completion-1 intervals over
  first→last token time; stored via `store.UpdateModelBench`.
- `models.bench_tok_per_s` / `bench_at` (migration 0003); manual override via
  PATCH clears `bench_at`.
- Price calculator (`AdminModels.tsx`) asks the admin to type PP speed by hand;
  TG speed is prefilled from `bench_tok_per_s`.

## Approach

- **Second pass in the same handler**, after the TG pass:
  - Prompt: ~10k tokens of randomized filler prose (random word order per run
    so the engine's prefix cache never serves the prompt from cache). Word
    count scaled down when `context_length` is set and small (< ~13k).
  - Request: same streaming + `include_usage`, `max_tokens=1`.
  - PP tok/s = `usage.prompt_tokens` ÷ (request sent → first streamed token).
    Prefill completes before the first token is emitted, so TTFT ≈ prefill.
  - PP failure (HTTP error, no usage, no streamed token) never voids the TG
    result: TG is stored, response carries `pp_error`, previous PP value is
    kept.
- **Storage:** migration `0009` adds `models.bench_pp_tok_per_s REAL NOT NULL
  DEFAULT 0`. `UpdateModelBench` takes an optional PP value (nil = keep old).
  `UpdateModelMeta` accepts a manual `bench_pp_tok_per_s` (clears `bench_at`,
  same semantics as TG).
- **API:** benchmark response gains `bench_pp_tok_per_s`, `prompt_tokens`,
  `pp_seconds` (or `pp_error`); `Model` and `GET /api/models` gain
  `bench_pp_tok_per_s`; admin PATCH accepts it.
- **UI:** admin metrics row shows editable "TG tok/s" and "PP tok/s"; the
  benchmark toast reports both; price calculator prefills `ppTps` from the
  measured value (same rule as TG). Public catalog table shows a TG and a PP
  column.

## Decisions

| # | decision | why | alternatives considered |
|---|---|---|---|
| 1 | TTFT as the PP timer, `max_tokens=1` | prefill dominates TTFT at 10k tokens; no engine-side stats endpoint needed | parse llama.cpp/vLLM timing stats (engine-specific, not OpenAI-compatible) |
| 2 | randomized prompt per run | prefix cache would otherwise measure cache reads, not prefill | fixed prompt (wrong); timestamp seed only (same first tokens still cached — full shuffle needed) |
| 3 | PP failure keeps old PP value, TG still saved | one flaky pass must not wipe good data or fail the whole benchmark | fail the whole request; zero out PP |
| 4 | ~10k token target, capped at ¾ of `context_length` | user-requested size; small-context models must not 400 | fixed 10k always |
